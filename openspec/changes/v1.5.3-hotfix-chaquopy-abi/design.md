## Context

See `proposal.md` for background and motivation. The v1.5.2 release build failed during Gradle's **configuration** phase, not execution: Chaquopy's `PythonPlugin.afterVariant` calls `getAbis`, which cross-references the configured Python version against the ABIs it ships runtimes for, and throws when `armeabi-v7a` is requested with Python 3.12. Because this happens in `afterEvaluate`, no task selection can avoid it — building only `assembleDebug` still trips the assertion for that variant.

This is the third consecutive hotfix on the same workflow step: `v1.5.1` de-duplicated release triggers, `v1.5.2` migrated Chaquopy to the Kotlin DSL, and `v1.5.3` clears the ABI assertion. The recurrence motivates the Node 0 work in this change — the repository had no Claude Code configuration and no captured hotfix convention, so each iteration re-derived the same context from archive archaeology.

## Goals / Non-Goals

**Goals:**
- Make `gradle assembleDebug` reach task execution on the GitHub runner, with no `GradleException` from `PythonPlugin.getAbis`.
- Keep the APK's embedded Python runtime on the same version the backend is tested against (3.12).
- Eliminate every `Node.js 20 is deprecated` annotation from both workflows.
- Make the APK's internal version identity match the release tag.
- Give Claude Code first-class support in the repository without forking the `.agent/` workflow definitions, and make the `token_efficiency` rules in `openspec/config.yaml` actually true.

**Non-Goals:**
- Upgrading Chaquopy, AGP, Kotlin, or Gradle versions — one variable at a time, same reasoning as `v1.5.2`.
- Publishing a signed `assembleRelease` APK instead of the current `assembleDebug` artifact. That requires a keystore plus repository secrets and is release engineering, not a hotfix.
- Fixing `package.json` → `android:build`, which invokes a `./gradlew` wrapper that does not exist in `android/` (CI uses the `gradle` binary installed by `setup-gradle`). Recorded here so the trail is not lost.
- Changing the Python dependency list bundled into the APK, the game protocol, or any frontend/backend behavior.

## Decisions

### 1. Drop `armeabi-v7a` rather than downgrade Python to 3.11
- **Decision**: Set `abiFilters += listOf("arm64-v8a", "x86_64")` and keep `chaquopy.defaultConfig.version = "3.12"`.
- **Rationale**: `pyproject.toml` declares `requires-python = ">=3.12"` and CI runs the backend suite on 3.12. Downgrading the embedded runtime to 3.11 would make the server execute inside the APK on a different interpreter than the one validated by the coverage and type gates — a silent divergence between what CI proves and what a user runs. The alternative cost is narrow: `armeabi-v7a` only serves 32-bit ARM devices, essentially pre-2016 hardware; `arm64-v8a` covers all modern devices and `x86_64` covers emulators.
- **Alternatives Considered**: (a) Python 3.11 with all three ABIs — rejected for the divergence above. (b) Per-ABI Python version via variant configuration — rejected as substantial build complexity to serve a device class the project has no stated requirement for.

### 2. Pin actions to the lowest `node24` major, not to `latest`
- **Decision**: `checkout@v5`, `setup-node@v5`, `setup-java@v5`, `setup-python@v6`, `setup-uv@v7`, `setup-android@v4`, `setup-gradle@v5`.
- **Rationale**: The goal is removing a runtime deprecation, not adopting new action features. Each target was chosen by reading the `runs.using` field of that tag's `action.yml` via `gh api` and taking the first major that reports `node24` — this minimizes the breaking-change surface. Notably `astral-sh/setup-uv@v6` is still `node20`, so `v7` is the minimum there, whereas jumping every action to `latest` would have moved `checkout` to v7 and `setup-uv` to v10 for no benefit.
- **Alternatives Considered**: (a) Setting `ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION=true` as the deprecation notice offers — rejected: it suppresses the symptom, pins the workflow to an unsupported runtime, and the name states the security trade-off. (b) Upgrading to `latest` majors — rejected as gratuitous breaking-change exposure in a hotfix.
- **Deliberate exclusion**: `softprops/action-gh-release@v2` does not appear in the deprecation list and is left untouched — it owns the asset upload, the step most costly to regress.

### 3. Bridge `.agent/` into `.claude/` with thin pointers, not copies
- **Decision**: Each of the 12 files in `.claude/skills/` and `.claude/commands/` carries only the frontmatter needed for discovery plus one line directing the agent to read the canonical file under `.agent/`.
- **Rationale**: The `.agent/` tree holds 2,242 lines of workflow definitions generated by the OpenSpec CLI (`generatedBy: 1.8.0`). Copying them creates a second source of truth that will silently diverge at the next `openspec update`. A pointer costs one extra file read per invocation and keeps `.agent/` authoritative for both agents.
- **Alternatives Considered**: Symlinking `.claude/skills` → `../.agent/skills` — rejected because it depends on unverified symlink-resolution behavior in Claude Code's skill discovery, and a silent discovery failure is worse than an explicit indirection.

### 4. Filter the generated Android sync directories from agent search
- **Decision**: Add `android/app/src/main/python/server/` and `android/app/src/main/assets/client_dist/` to all three ignore files.
- **Rationale**: Both are build-time copies of `server/` and `client/dist/` produced by the "Sync ..." workflow steps; they are already in `.gitignore`. Left unfiltered they double every code search hit and invite edits to the copy instead of the source. Note the sibling `android/app/src/main/python/android_entry.py` is genuine source and stays searchable — only the `server/` subdirectory is filtered.

## Risks / Trade-offs

- **[Risk] Users on 32-bit ARM devices can no longer install the APK** → **Mitigation**: Accepted and documented in `REQ-AND-007`. The device class is pre-2016 hardware and the project has no stated requirement for it; the alternative (a Python runtime divergent from the tested backend) carries a worse failure mode — a bug reproducible only on device.
- **[Risk] An action major bump introduces an unrelated breaking change** → **Mitigation**: Minimum-jump selection verified per action against `runs.using`; all existing inputs are preserved verbatim; and the `workflow_dispatch` dry-run exercises the full release path before any tag is published.
- **[Risk] The `.claude/` pointer files drift from the `.agent/` frontmatter they mirror** → **Mitigation**: Only `name`/`description`/`allowed-tools` are duplicated — the fields required for discovery. Behavior lives in exactly one place, so drift degrades a description, never the workflow itself.
- **[Risk] The dry-run passes but the tagged release still fails** → **Mitigation**: `workflow_dispatch` runs the identical job; the only divergent step is the upload, which is guarded by `if: startsWith(github.ref, 'refs/tags/') || github.event_name == 'release'` and was already proven working in v1.5.0.
