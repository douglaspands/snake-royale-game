## Context

See `proposal.md` § Why. Two independent defects, both on the touch path, both post-`v1.6.0`:

1. `_sendCurrentInput()` picks the transmitted angle with `virtualJoystick.isActive() ? joystick.getAngle() : desktopController.getAngle()`. Two things make that fallback unsafe: a duplicate `window.mousemove` listener in `main.ts` (in addition to `DesktopController`'s own internal one) feeds touch-synthesized pointer coordinates into `DesktopController`'s stored angle unconditionally; and even without that contamination, `isActive() === false` is not the same as "the desktop controller is the intended input source" — it only means no finger is currently down.
2. `GameWebViewActivity` enables the legacy wide-viewport/overview pair, which shrinks a page that already declares `width=device-width`. The client's `100vw` sizing and visual-viewport measurement are the trigger that keeps that shrink-to-fit path reachable.

The two are unrelated in mechanism but ship together because they are the same user-visible complaint — "the mobile game does not behave like the browser game" — and because they are cleanly separable into disjoint work lanes.

## Goals / Non-Goals

**Goals**
- The transmitted heading angle tracks whichever control scheme the player actually last used.
- Mouse-aim is immune to synthetic pointer events generated by touch input.
- "Jogar no App" presents the game at 1:1 page scale, filling the activity window exactly as the system browser does.
- The client can never make the document wider or taller than the layout viewport.

**Non-Goals**
- Reworking the virtual joystick's rendering, deadzone, or double-tap boost gesture — unaffected.
- Adding a "neutral/stop" heading state. This game is continuous free-steering by design; the fix is about *which* last-known angle is honoured, not introducing a stop state.
- Server-side changes. The server already relays `target_angle` verbatim (`REQ-PROTO-003`).
- Display-cutout letterboxing (`layoutInDisplayCutoutMode = shortEdges`). The reported symptom is shrink-to-fit, not a black bar beside the punch-hole camera. If device evidence later shows letterboxing in landscape, that is a separate change.
- Edge-to-edge / `WindowCompat.setDecorFitsSystemWindows`. The current immersive implementation already produces a full-bleed window; nothing in the report contradicts that.

## Decisions

### D1 — Gate mouse-aim on `PointerEvent.pointerType === 'mouse'`, not on `MouseEvent`
Browsers dispatch a synthetic `mousemove`/`mousedown` after touch interaction for legacy-site compatibility, but `pointermove` carries a `pointerType` that distinguishes real mice from touch and pen. Switching `DesktopController`'s internal listener to `pointermove` + type check closes the contamination at the source. *Alternative considered:* keep `mousemove` and heuristically filter by movement pattern — rejected as unreliable and more complex than using the type the browser already reports.

### D2 — Remove the duplicate listener in `main.ts` rather than reconciling two copies
`DesktopController._bindEvents()` already listens on `window` and computes the identical `atan2` angle. The `main.ts` copy, and the `setMousePosition()` method it drives, are redundant. Deleting both is simpler than keeping two listeners in sync.

### D3 — Track "last active input source" explicitly instead of inferring it from `isActive()`
`_sendCurrentInput()` remembers which controller's `onInputChange` fired most recently and reads that controller's angle, regardless of the joystick's current `isActive()` state. `VirtualJoystick.getAngle()` already retains its last angle after `handlePointerUp`, so `VirtualJoystick` itself needs no change.

### D4 — Disable `useWideViewPort` and `loadWithOverviewMode` rather than compensating for them
Those two settings exist to render pages written for desktop widths: `useWideViewPort` honours a wide layout viewport (defaulting to ~980 CSS px when the page gives no viewport meta), and `loadWithOverviewMode` then zooms the page out until that content width fits the screen. `client/index.html` already declares `width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no`, so the emulation contributes nothing and only the shrink-to-fit survives. Disabling both makes the WebView lay out at device width and page scale 1.0. *Alternative considered:* keep them and force `setInitialScale(100)` — rejected, because a forced initial scale fights the viewport meta and still leaves the overview zoom-out reachable on any layout overflow.

### D5 — Measure the layout viewport, not the visual viewport
`window.innerWidth`/`innerHeight` report the *visual* viewport, which in a WebView is the layout viewport divided by the current page scale. Sizing the canvas from it while the page scale is being decided is circular: a canvas one sub-pixel too wide is horizontal overflow, overflow triggers overview zoom-out, the zoom-out changes `innerWidth`, and the next `resize` re-sizes the canvas from the new value. `document.documentElement.clientWidth`/`clientHeight` report the layout viewport, are unaffected by page scale, and are exactly what CSS `100%` resolves against — which is why D6 pairs with this. With `html, body { overflow: hidden }` already in place, the two measurements are identical on desktop, so this is a no-op there.

### D6 — `#app` sized `100%`, not `100vw`/`100vh`
`100vw` is the viewport width *including* any scrollbar gutter, and in WebViews it can round differently from the layout viewport. `html, body` are already `width: 100%; height: 100%`, so `#app { width: 100%; height: 100% }` inherits an exact box that cannot overflow. Keeping `100vw` would leave D4's shrink trigger armed for any future WebView that re-enables overview mode.

### D7 — Three parallel sub-agent lanes over isolated git worktrees
The work splits into three file sets that barely intersect, so it is executed by three sub-agents (sub-sessions), each in its own git worktree, launched together after Node 0 gates the specs. See § Parallel execution for the contracts. *Alternative considered:* one sequential session — rejected because the Android lane requires no TypeScript context and the two client lanes touch disjoint methods, so serialising them buys nothing but wall-clock time.

## Parallel execution

Node 0 (spec validation) runs in the orchestrator session and **must** pass before any lane starts — the SDD rule in `CLAUDE.md` admits no production code before its spec is validated. The three lanes then run concurrently; Node INT and Node DOC run in the orchestrator after all lanes have merged.

| Lane | Sub-agent | Owns requirement | May touch | Must not touch |
| :--- | :--- | :--- | :--- | :--- |
| **A — Android host** | `android-webview-viewport` | `REQ-AND-004` | `android/app/src/main/java/com/snakeroyale/host/GameWebViewActivity.kt`, `android/app/build.gradle.kts` | anything under `client/`, `server/` |
| **B — Client input** | `client-input-source` | `REQ-PROTO-007` | `client/src/input/desktop_controller.ts`, `client/tests/input.test.ts`, and only `_setupInputListeners()` / `_sendCurrentInput()` / the input fields in `client/src/main.ts` | `client/src/index.css`, `_setupResize()`, anything under `android/`, `server/` |
| **C — Client viewport** | `client-viewport-sizing` | `REQ-REND-005` | `client/src/index.css`, and only `_setupResize()` / the `Camera` construction in `client/src/main.ts`, `client/tests/` files covering resize | `client/src/input/`, `_setupInputListeners()`, `_sendCurrentInput()`, anything under `android/`, `server/` |

**Isolation.** Each lane is launched with `isolation: "worktree"` so it builds and tests against its own checkout without seeing partial work from the others.

**Conflict boundary.** Lane A is disjoint from B and C. Lanes B and C both edit `client/src/main.ts`, but in methods that do not overlap; the table above is the authoritative boundary. Merge order is **B before C** — B deletes a block from `_setupInputListeners()`, which shifts the line numbers C's hunks anchor to, so C rebases onto B rather than the reverse.

**Lane contract.** Every lane must, before reporting complete: (1) keep its own capability's scenarios satisfied; (2) run `cd client && npm test` (lanes B, C) or confirm its module compiles under the constraints in `tasks.md` (lane A, which has no local Gradle toolchain); (3) report the exact files it changed and any file it needed outside its allowlist — a lane that needs to cross the boundary stops and reports instead of editing.

**What stays in the orchestrator.** Node 0, the merge, Node INT (the full `npm test` + `npm run lint` gate over the merged tree), Node DOC, and every on-device validation task in Node VAL. Lanes never run the root gate — a lane's worktree contains only its own third of the change and would gate an incomplete tree.

## Risks / Trade-offs

- **[Risk]** A stray real mouse-move on a hybrid touch+mouse device (e.g. a Chromebook) after joystick use switches the source back to mouse-aim mid-match. → This is correct per `REQ-PROTO-007`'s third scenario and matches the existing intended UX — mouse aim is instant-reflex by design — and only genuine mouse pointer events trigger it.
- **[Risk]** `client/tests/input.test.ts` dispatches raw `mousemove` events to exercise `DesktopController`; switching the listener to `pointermove` breaks that test unless updated. → Updated in lane B, in scope.
- **[Risk]** Disabling `useWideViewPort` changes layout for any page the WebView loads, not just the SPA. → The activity loads exactly one URL, the bundled SPA, which declares its own viewport. No other page is reachable from it.
- **[Risk]** The shrink-to-fit diagnosis is inferred from the code and the reported symptom, not from a device capture. If the on-device evidence in Node VAL shows the window itself is inset rather than the page being scaled, D4/D5/D6 will not be sufficient. → Node VAL captures the evidence (screenshot plus `window.devicePixelRatio`, `visualViewport.scale`, `documentElement.clientWidth` from the WebView console) *before* declaring the lane done, so a wrong hypothesis surfaces as a failed validation rather than a silent non-fix.
- **[Trade-off]** Three worktrees cost setup and a merge step for a change of this size. → Accepted: the lanes have near-zero shared surface, and the Android lane in particular carries no TypeScript context at all.
